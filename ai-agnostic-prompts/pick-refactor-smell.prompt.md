# pick-refactor-smell · prompt

> **触发场景**：当用户想从 docs/features/F*.json 的 notes 字段里挑一个代码坏味道（TODO / suggest / 待重构项）出来重构时使用。本 skill 负责扫描全部 feature notes、按固定严重性 rubric 排序、给出推荐和候选清单，并在用户选定后 hand off 到 plan 模式做实际重构。本 skill 不写代码、不 commit，只做发现和选择。触发短语示例："挑一个坏味道重构"、"从 feature-list 找个待重构项"、"扫一下 suggest"、"看看 notes 里有什么待办的代码气味"。
>
> **用法**：把"# pick-refactor-smell"以下的全部内容粘到你 AI 对话窗口，AI 会按里面的步骤工作。

---


# 挑选代码坏味道

本 skill 把"从 feature notes 里挑一个待重构项"当作三阶段工作流：扫描 → 排序 → 选择。完成后 hand off 给用户继续走 plan 模式实际重构。

> 重要：本 skill 与用户交互一律使用中文。

---

## 适用范围

- ✅ 用户想做一次代码重构，但不确定该挑哪个 → 本 skill 给出推荐
- ✅ 用户指定某个 feature/某类气味（如「只看 F052 的 suggest」、「只看跨文件的」）→ 本 skill 帮聚焦
- ❌ 用户已知要做哪个 → 不用本 skill，直接进 plan 模式
- ❌ 用户描述了 notes 之外的问题（外部观察、bug 报告）→ 不用本 skill，直接进 plan 模式

---

## 全局原则

1. **只做发现和选择，不写代码、不修改任何文件**。选定后告诉用户「现在进入 plan 模式开始重构 X」并停止。
2. **严重性 rubric 不主观**：严格按下述固定标准评分，避免每次结果飘移。
3. **覆盖优先于精简**：宁可多列几个候选让用户挑，也不要漏掉关键项。
4. **不调用其他 skill**：本 skill 是入口，下游交给用户的下一句话。

---

## 阶段 1：扫描

**进入条件**：用户触发本 skill。

**产出**：未排序的候选清单。

**行为**：

1. 检查 `docs/features/` 目录是否存在：
   - 不存在 → 提示用户「先跑 generate-feature-list 初始化 feature 详情目录」，本流程终止。
   - 存在 → 继续。

2. 遍历 `docs/features/F*.json` 全部文件，读取每个文件的 `notes` 字段。

3. 对每个 `notes` 字段，提取包含下列任一关键词的段落（按换行或句号分段）：
   - `TODO`
   - `suggest`
   - `代码气味` / `Code smell`
   - `重构`
   - `未来` / `推到`

4. 每条候选记录至少含：
   - feature id（如 `F052`）
   - feature 简要 title（从主索引 `docs/feature-list.json` 取，一句话）
   - 原文片段（≤200 字，原样摘抄，不改写）
   - 涉及的代码文件路径（若 notes 里有提及，如 `scripts/pawn/pawn.gd`）

5. 若扫描结果为空：
   - 输出「当前所有 feature 的 notes 中无未处理代码气味，项目处于干净状态。如有外部观察到的问题，请直接描述。」
   - 本流程终止，不进入阶段 2。

---

## 阶段 2：按固定 rubric 排序

**进入条件**：阶段 1 找到至少 1 条候选。

**产出**：分级的候选清单。

### 严重性 rubric（固定，不可灵活解释）

**🔴 高严重（任一即满足）**：
- 涉及 **3+ 文件**（按 notes 中提及的文件路径数 + 实际影响推断）
- 已知造成过 bug（notes 中含 `出过 bug` / `踩坑` / `BUG` / `bug` / `修了 N 次` 等表述）
- 阻碍后续 feature 开发（依赖此项的 pending feature ≥ 2，可通过查 `docs/feature-list.json` 主索引的 `depends_on` 反向推导）

**🟡 中严重**（高不满足，且满足任一）：
- 单文件局部，但影响可维护性（如硬编码常量、SRP/DRY 违反）
- 重复模式（2 处硬编码 / 跨文件共用常量耦合）
- 命名混淆 / 职责混乱（如布尔参数承担两件事）

**🟢 低严重**（其他）：
- 风格偏好（如 dict 驱动 vs 多个常量）
- 微小改进
- 已被后续 feature 解决（notes 中明确说"已由 F0YY 替代"等）

### 排序时的辅助判断

- 多条候选同 feature id 时，逐条独立评分（同一 feature 可能有 2 条不同气味）
- 跨 feature 引用同一文件的多条候选 → 标注「同文件叠加」，作为高严重加分项
- 若候选明确写明「TODO（feature 完成后留下，按上条改造）」这类强相关链条，列出依赖

---

## 阶段 3：输出报告并停止

**进入条件**：阶段 2 完成排序。

**产出**：报告 + 推荐 + 等用户挑。

### 固定输出格式

```
## 代码坏味道扫描报告（共 N 项候选）

### 🔴 高严重（M 项）
1. **F0XX：<一句话 title>** | 涉及：`scripts/...`
   原文：「<≤200 字原文片段>」
   理由：<符合 rubric 哪一条，一句话>

### 🟡 中严重（K 项）
2. **F0YY：...** | 涉及：`...`
   原文：「...」
   理由：...

### 🟢 低严重（L 项）
3. **F0ZZ：...** | 涉及：`...`
   原文：「...」
   理由：...

### 推荐

建议优先重构 **F0XX：<title>**。
理由：<一句话对比，说明为什么比其他高严重项更值得先做——例如"已造成过 bug" / "依赖最多" / "影响 N 个 HUD feature"等>。

---

下一步：进入 plan 模式后告诉我「重构 F0XX」即可开始走 plan workflow（探索 → 设计 → 实现 → 验证 → commit）。
```

### 关键约束

- 高/中/低三档按数量排序内编号（不重置编号），便于用户引用「重构第 N 条」
- 推荐**有且只有一条**（不给多个推荐让用户挑——AI 已经做了判断）
- 推荐理由必须**对比**，不能只说被推荐项的优点
- **不进 plan、不开 Explore agent、不写代码**——等用户回复

---

## 用户回复后的行为

| 用户回复 | 行为 |
|---|---|
| 「重构 F0XX」/「就它了」/「按推荐来」 | 提示用户「现在按 `/plan` 或直接说"进 plan 模式开始重构 F0XX"」，本 skill 结束 |
| 「想看 F0YY 完整 notes」 | 用 `cat docs/features/F0YY.json` 展示完整 notes，再问要不要选它 |
| 「这些我都看过了，再扫一遍但只看 X 类」 | 用 X 类作为过滤条件重跑阶段 1-3 |
| 「都不想做」/「先这样」 | 「好，本次不重构。下次需要时再叫我」，本 skill 结束 |

---

## 与其他 skill 的关系

- **本 skill 是入口**：用户的下一句决定下游走向（一般是「重构 F0XX」+ 进 plan 模式）
- **不调用** `generate-feature-list` / `sync-feature-list` / `execute-next-feature`：
  - `generate-feature-list` 是从零生成 feature-list
  - `sync-feature-list` 是源文档变更后同步
  - `execute-next-feature` 是实现新 pending feature，**不适合**回头重构已 done feature 引入的气味
- **实际重构走 plan 模式**：因为重构需要按问题特点灵活探索（决定改几个文件、引入什么模式、要不要拆 commit），plan workflow 已经把这部分管得很好

---

## 异常处理

| 情况 | 处理 |
|---|---|
| `docs/features/` 不存在 | 提示「先跑 generate-feature-list」，停止 |
| `docs/features/F*.json` 任一文件 JSON 不合法 | 报错该文件路径，停止（先让用户修文件再重试） |
| 所有 notes 都无关键词命中 | 输出「当前所有 feature 的 notes 中无未处理代码气味，项目处于干净状态」，停止 |
| 候选超过 15 条 | 提示「候选较多，建议先做高严重 + 中严重 top 3，是否要我只列这部分？」，按用户回复决定 |
| 用户回复语义模糊（如「嗯」） | 不假设，直接问「按推荐 F0XX 走还是选别的？」 |
